# Bench baselines (`benchmarks/baselines/`, plan §6.3 item 5, ADR-0054 / ADR-0101)

A *baseline* is a `bench_result.json` written by `wintersar bench` (schema in ADR-0054) that the
nightly workflow (`.github/workflows/nightly.yml`, job `compare-baseline`) compares the fresh
run against with `wintersar.bench.report.compare` (regression = a stage whose median wall time
is more than `regression_threshold` — 15 % by default — slower). Numbers live only in these JSON
files and in the generated comparison tables, never in prose (rule 11.8).

## File naming: one baseline per runner class

```
benchmarks/baselines/<site>.<runner-class>.json      e.g. S_synthetic.ubuntu-24.04.json
```

Wall time, RSS and disk figures are properties of the machine that produced them, so a baseline
is only comparable with runs on the **same runner class**. `<runner-class>` is the exact
`runs-on` label of the job that consumes the file (`RUNNER_CLASS` in `nightly.yml`, currently
`ubuntu-24.04` — an explicit image, not `ubuntu-latest`, so the file keeps its meaning when the
`-latest` alias moves to a newer OS). A laptop result must never be committed under a hosted-runner
name; if you benchmark elsewhere, use your own label (for example `S_synthetic.m2-16gb.json`) and
do not expect the nightly job to pick it up.

## Status: report only (open question #58)

Which runner class to baseline on — and whether a GitHub-hosted runner is stable enough for a
15 % gate on the synthetic S site at all — is `docs/open-questions.md` #58. Until it is resolved:

- `.github/workflows/ci.yml` and the nightly `bench` job only *measure* and upload
  `bench_result.json` as an artifact;
- the nightly `compare-baseline` job reads `benchmarks/baselines/S_synthetic.<runner-class>.json`
  **when it exists**, writes the before/after table to the job summary and turns the job red on a
  regression, but runs with `continue-on-error: true`, so the workflow never fails because of it;
- when no baseline file exists the job just notes that in the summary.

Turning the comparison into a gate (`--fail-on-regression`, a non-`continue-on-error` job) is the
decision that closes #58 and needs an ADR.

## How to create a baseline

1. Measure the variance first (the #58 method): download the `bench-S_synthetic-<runner-class>`
   artifacts of several nightly runs (10 is the number the open question asks for) at commits
   with no performance-relevant change and look at `total.wall_time_s` and the per-stage
   `wall_time_s_runs`. If the spread exceeds the threshold, raise `--repeats` or the site's
   `regression_threshold` before committing a baseline, or switch to a self-hosted runner class.
2. Pick the artifact of a run on the default branch at a known-good commit **on the runner class
   the file is named after**. Do not generate the file on a developer machine.
3. Commit it as `benchmarks/baselines/S_synthetic.<runner-class>.json` (the `.gitignore` pattern
   `bench_result*.json` does not match this name). The PR body states the commit/run it came from.
4. From then on `wintersar bench --site benchmarks/sites/S_synthetic.yaml --compare
   benchmarks/baselines/S_synthetic.<runner-class>.json --markdown bench.md` renders the table
   locally; the nightly job does the same automatically.

## How to update a baseline

Only deliberately: after an intended slowdown (a new correctness step, a bigger site definition)
or a runner image change. Replace the file with a fresh artifact from the same runner class and
say why in the PR body, quoting the comparison table generated by `--compare` (not typed numbers).
A baseline is *not* refreshed to make a red comparison green.
